# ADR-002 — Correlation and timeout strategy for order aggregation

**Status:** accepted  
**Date:** 2026-10-04

## Context

PA3 splits one order into multiple item messages that can travel through different worker queues and return in a different order. The aggregator therefore needs a reliable way to know which results belong to the same order and when an order is finished.

The aggregator also cannot wait forever if one worker fails to return a result. Duplicate deliveries are possible as well, so simply counting every received message could incorrectly mark an order as complete.

## Decision

The router preserves correlation by putting the original `orderId` in both `orderId` and `correlationId` on every split item message. It also includes `itemIndex` and `totalItems`. Workers must preserve these fields so the aggregator can reconstruct the order correctly.

The aggregator stores in-flight orders in an in-memory dictionary keyed by `orderId`. For each order, results are stored in another dictionary keyed by `itemIndex`. This means a duplicate result for the same item replaces the existing value instead of increasing the number of received items.

An order is complete when the number of distinct item indexes received equals `totalItems`. The aggregator then publishes one message to `orders.complete` with status `complete` and an empty `missingItemIndexes` list.

I use a 5-second idle timeout, configurable through `AGGREGATOR_IDLE_TIMEOUT_SECONDS`. The last-activity timestamp is reset whenever a result arrives. A background sweep runs every second. If an incomplete order has received no new results for more than the idle timeout, the aggregator publishes a `partial` result containing the results received so far and the exact item indexes that are missing.

For an unsupported item type, the router logs the unknown type and does not publish it to an incorrect worker queue. This avoids silently routing an item to a worker that cannot process it.

## Alternatives considered

A fixed timeout measured from when the first result arrived was considered. I chose an idle timeout instead because a larger order may legitimately take longer overall while still making progress. Resetting the timer whenever a result arrives prevents an actively progressing order from becoming partial simply because its total processing time exceeds five seconds.

I also considered storing aggregation state in an external system such as Redis. That would make the state survive aggregator restarts and would work better with multiple aggregator instances. For this assignment, an in-memory dictionary is simpler and sufficient for the expected scale.

Another alternative was to store results in a list and count every received message. I rejected this because RabbitMQ can redeliver messages. Keying results by `itemIndex` naturally makes duplicate deliveries idempotent for the aggregation count.

## Consequences

Correlation remains explicit throughout the message flow, and concurrent orders remain separated because aggregation state is keyed by `orderId`. Duplicate item results do not cause premature completion, and callers receiving a partial result can see exactly which item indexes are missing.

The idle timeout allows an order to make progress for longer than five seconds as long as results continue arriving, while still preventing an abandoned order from remaining in memory forever.

The main limitation is that aggregation state exists only in process memory. If the aggregator container restarts while orders are in flight, that state is lost. An external persistent state store would be needed for stronger recovery and horizontal scaling. Large numbers of simultaneous orders or orders containing hundreds of items would also increase memory usage in the aggregator.
