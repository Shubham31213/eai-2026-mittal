# ADR-003 — Canonical Order Translation and Pricing Enrichment

**Status:** accepted  
**Date:** 2026-10-12

## Context

PA4 requires three different order formats to produce the same canonical order structure without changing the provided JSON schema.

The Web source uses nested JSON with a payment object inside `customer`. The Mobile source uses abbreviated field names, numeric currency and status codes, a Unix timestamp in seconds, and payment fields named `pm`, `pan`, and `pexp`. The B2B source uses XML encoded as Windows-1257, with payment details under `BuyerParty`.

Product identifiers also differ: Web uses `PROD-001`, Mobile uses `001`, and B2B uses `SKU-PROD-001`. The B2B XML parser prefixes attributes with `@_` and may return a single `LineItem` as an object rather than an array.

The source files do not provide trusted prices. The pricing API can also return 404 for unknown products or other errors such as 500.

## Decision

I implemented three translators: `translateWeb()`, `translateMobile()`, and `translateB2B()`. Each reads its own source format and constructs a new `CanonicalOrder` object using only fields allowed by the fixed schema.

Shared helper functions normalize product IDs, convert mobile timestamps and status codes, map currencies, and parse addresses. For B2B XML, `decodeB2BXmlBytes()` uses `TextDecoder("windows-1257")` before parsing to preserve Latvian characters. The B2B translator also converts a single XML line item into an array before processing it.

Every line item obtains its price, currency, and tax rate through `enrichFromPricing()`. The `toDecimalAmount()` function uses `toFixed(2)` to preserve the required decimal-string representation; for example, `4.5` becomes `"4.50"`.

If the pricing API returns 404, the item is excluded and an `UNKNOWN_PRODUCT` warning is recorded. Other API failures produce `PRICING_API_ERROR` warnings. Processing continues for the remaining items. If no items can be priced, the translator returns `order: null` with the collected warnings.

Sensitive payment data is removed through explicit field selection. The Web translator never copies `customer.payment`; the Mobile translator never copies `pm`, `pan`, or `pexp`; and the B2B translator never copies `PaymentDetails`.

Unknown currency codes and unsupported status values produce errors rather than silently creating invalid canonical values.

## Alternatives considered

One alternative was to reject an entire order whenever one product could not be priced. I rejected this because a single unavailable product should not prevent other valid products from being processed. Returning warnings makes the partial result visible.

Another alternative was to use prices embedded in source files, especially B2B `UnitListPrice`. I rejected this because those values may be outdated. The pricing API is the trusted source.

I also considered copying source objects and deleting sensitive fields afterward. Explicitly constructing the canonical output is safer because new or unexpected payment fields cannot accidentally pass through.

## Consequences

The three source systems now produce structurally consistent canonical orders, and sensitive payment details are excluded. Shared helper functions also reduce duplicated transformation logic.

The main cost is additional dependence on the pricing API. Every product requires a request, and unavailable products may result in partial orders or `order: null`. The warnings allow downstream systems to distinguish these outcomes from successful complete orders.

The fixed canonical schema creates another maintenance cost. If it gains a new required field, all three translators must be updated. A fourth source with a different product identifier format would require an additional normalization rule and tests.

For a production system, I would add schema validation inside the translation pipeline, structured logging for warnings, and controlled retries for temporary pricing API failures.
