# ADR-005 — Sequential checkout saga with compensation

**Status:** accepted  
**Date:** 2026-10-29

## Context

The checkout process depends on four separate services: payment, inventory, shipping, and notification. They must run in order because a later step should not start if an earlier step fails. Payment and inventory have compensating endpoints, but shipping and notification do not. This means a shipping or notification failure can require releasing reserved inventory and refunding payment, even though the earlier work cannot simply be erased.

Idempotency also needed careful handling. A repeated request with the same key and payload should return the original result, while a different payload using the same key must receive HTTP 409. A request arriving while the first one is still running must also receive a conflict response. Timeouts need to be distinguished from ordinary service failures because timeout-triggered checkout failures return HTTP 504, while business failures return HTTP 422.

## Decision

I implemented the checkout orchestration in `server.ts` using sequential calls through `callService`. The payment authorization runs first, followed by inventory reservation, shipping creation, and notification. Each step starts only after the previous step succeeds.

The `runStep` function records each step's status, timestamps, and duration in the trace. When checkout fails, completed compensatable steps are rolled back in reverse order: inventory is released first, then payment is refunded. If compensation fails, the response uses the `compensation_failed` code. Axios timeout errors are handled separately from ordinary downstream failures.

The idempotency store records the request hash, state, HTTP status, and response. A replay with the same key and payload returns the stored status and response instead of running the saga again. A different payload with the same key receives HTTP 409 with `idempotency_payload_mismatch`.

## Alternatives considered

One alternative was to call independent services in parallel to reduce checkout time. I rejected this because the required process is sequential, and parallel execution could create side effects even when an earlier step fails.

Another option was to add compensation endpoints to shipping and notification. That would allow more complete rollback, but those services are outside the orchestrator's control and their contracts do not provide such endpoints. I therefore accepted that compensation can only undo payment and inventory operations.

I also considered returning an immediate pending response and processing the saga asynchronously. I kept the synchronous flow because it fits the current assignment and allows the caller to receive the final result directly.

## Consequences

Sequential execution makes the trace easier to understand and prevents later steps from running after an earlier failure. Persistent idempotency records also allow completed responses to be replayed after a restart. However, the synchronous flow can take longer when a service is slow, and a timeout does not guarantee that the downstream service did no work.

Adding a fifth step will require updating the sequence, failure handling, trace, and compensation logic. Requests using different idempotency keys but the same order ID are not automatically protected from racing with each other. Compensation is also incomplete when a downstream service has no rollback endpoint. These limitations are accepted for this implementation.
