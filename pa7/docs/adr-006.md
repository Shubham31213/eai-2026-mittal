# ADR-006 — Durable checkout saga using Temporal

**Status:** accepted  
**Date:** 2026-11-08

## Context

In PA6, I implemented checkout orchestration directly in an Express request handler. The orchestrator called payment, inventory, shipping and notification services in sequence, using `callService()` and `runStep()` to handle HTTP calls, timeouts, errors and tracing.

PA6 also stored idempotency and saga information in JSON files. Before executing a checkout, it called `saveIdempotency()` with the `in_progress` state. If the orchestrator crashed before updating this record to a final state, a subsequent request using the same key would receive HTTP 409 `idempotency_conflict`. The implementation did not include an automatic recovery process for unfinished sagas.

This creates a reliability problem: external side effects may already have occurred, but the orchestrator can lose its execution position when the process terminates. A payment might have succeeded while the application has not yet completed inventory reservation or compensation.

PA7 addresses this problem by using Temporal to execute the checkout as a durable workflow. The PA7 public crash-recovery test confirmed that the workflow resumed after the worker restarted without authorizing payment twice. This is an observed PA7 result, not a claim that I separately performed the PA6 crash experiment.

## Decision

I implemented the checkout saga as a Temporal workflow in `pa7/worker/src/workflows/checkout.ts`, with HTTP interactions isolated in `pa7/worker/src/activities/index.ts`.

The workflow executes four forward activities in order: `authorizePayment`, `reserveInventory`, `createShipment` and `sendNotification`. It calculates the order amount using integer cents to avoid floating-point rounding errors.

Each activity has a `startToCloseTimeout` of 2500 milliseconds and a retry policy with a maximum of three attempts, an initial interval of 200 milliseconds and a backoff coefficient of 2. These settings bound individual attempts while allowing temporary downstream failures to recover.

The activity layer interprets successful HTTP responses as completion. Business failures returned as HTTP 4xx become non-retryable `ApplicationFailure` errors, while server errors and network failures remain retryable. The workflow distinguishes timeout failures from other activity failures.

Compensation remains explicit business logic. If inventory reservation succeeded, the workflow releases inventory when a later step fails. If payment authorization succeeded, it refunds the payment. Compensation runs in reverse order, and a compensation failure produces the `compensation_failed` result.

The workflow records a trace of completed and failed steps and returns a structured result rather than throwing an unhandled workflow failure.

## Alternatives considered

One alternative was to retain the PA6 Express orchestrator and implement recovery manually. This would require scanning persisted `in_progress` records on startup, determining which downstream operations actually completed, safely resuming unfinished steps and preventing duplicate side effects. It would also require implementing durable retry scheduling and coordinating multiple orchestrator instances. I rejected this approach because it would reproduce much of the functionality provided by Temporal.

Another alternative was to retry every failure. I rejected this because permanent business failures, such as a declined payment or refused inventory reservation, should not be retried automatically. Retrying these requests would increase unnecessary traffic and could repeat unwanted operations.

A third alternative was to implement the entire saga as one activity. This would reduce the number of activity definitions but would hide individual steps from Temporal and make retry and recovery behavior less precise. Separate activities provide clearer execution history and failure boundaries.

## Consequences

Temporal improves crash recovery and reduces the amount of retry and execution-state management that the application must implement itself. The PA7 tests demonstrated successful recovery after a worker restart, correct compensation after a shipping timeout, and consistent handling of repeated idempotency keys.

However, Temporal does not guarantee that an external HTTP side effect happens exactly once. In the crash-recovery scenario, an activity can be attempted again if the worker terminates before its successful completion is durably recorded. The test demonstrated that shipping was called twice. If payment authorization were repeated, the payment service would need an idempotency mechanism to avoid charging the customer twice.

Temporal workflows must also remain deterministic. Workflow code cannot freely perform HTTP requests, read arbitrary environment variables or depend on uncontrolled external state. Those operations belong in activities. Changes to workflow code during deployment must preserve compatibility with existing execution histories, potentially requiring workflow versioning or worker deployment strategies.

The system now also requires operating the Temporal server, maintaining its persistence, monitoring workflow and activity failures, and managing worker availability. These introduce infrastructure, operational complexity and resource costs that were not present in the same form in PA6.

Temporal therefore improves durability but does not eliminate the need for careful compensation design, idempotent downstream operations or production monitoring.

## What the engine took over

- **Activity timeouts:** In PA6, `callService()` configured the Axios timeout using `config.requestTimeoutMs`, and `runStep()` manually recognized timeout errors such as `ECONNABORTED`. In PA7, Temporal enforces `startToCloseTimeout` and reports `TimeoutFailure` through the workflow failure chain.

- **Retry execution and backoff:** In PA6, `runStep()` directly handled each downstream request and its failure result. In PA7, Temporal manages activity attempts using the configured maximum of three attempts, initial interval and exponential backoff. The application still decides which failures are non-retryable.

- **Durable execution progress:** In PA6, `saveSaga()` and `saveIdempotency()` maintained JSON records, while the actual execution position lived in the Express request handler. In PA7, Temporal records workflow and activity progress in durable execution history and can reconstruct workflow state after a worker restart.

- **Resuming interrupted execution:** In PA6, the `/checkout` handler returned `idempotency_conflict` for an existing `in_progress` record, without implementing a recovery worker. In PA7, Temporal schedules outstanding work when workers become available again, as demonstrated by the worker-restart test.

- **Activity scheduling and completion tracking:** In PA6, the `runStep()` function awaited HTTP calls and managed their results directly. In PA7, `proxyActivities()` schedules the activities and Temporal tracks their completion. The workflow still determines the sequence and records the business-level trace.

- **Retryable versus permanent failure handling:** In PA6, `runStep()` interpreted HTTP responses and Axios exceptions directly. In PA7, the activity layer classifies failures using `ApplicationFailure`, while Temporal applies the retry policy. Business error classification remains application responsibility.
