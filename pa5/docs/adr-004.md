## Context

The messaging layer needs to connect each order with the results produced by payment, inventory, and notification services. It also needs to handle temporary failures without retrying messages forever and prevent duplicate notifications when RabbitMQ delivers a message more than once. The main decisions were how to carry `correlationId`, when to send failed messages to the dead-letter queue (DLQ), and how to remember which notifications have already been processed.

## Decision

The order service generates a UUID for each accepted order and publishes it in the AMQP `headers.correlationId` field. The canonical order body remains unchanged, and each consumer copies the same header to its result event. I used a custom header rather than AMQP's native `properties.correlationId` to keep the identifier in the same place expected by this assignment's message flow.

The consumers allow three processing attempts, using the existing retry and dead-letter topology. When a message reaches the retry limit, it is sent to the DLQ instead of being requeued indefinitely. Notification service records processed correlation IDs in `/data/processed-ids.json` and appends notification entries to `/data/notification.log`. It checks the saved IDs before logging a notification, so a redelivered message with an already processed ID can be acknowledged without writing another notification.

## Alternatives considered

I considered using AMQP's native `properties.correlationId`, but chose the custom header because the existing message flow uses `properties.headers.correlationId`. Changing the location would require consistent updates to every publisher and consumer.

An in-memory `Set` would be simpler than a JSON file, but it would be cleared whenever the notification service restarted. A redelivered message could then be logged twice. Persisting IDs allows the service to retain its deduplication record across restarts.

I also considered allowing unlimited retries through requeueing. That could keep a failing message in circulation and make it harder to isolate a persistent failure. The three-attempt limit provides a clear point at which the message is moved to the DLQ for investigation.

## Consequences

The shared correlation header makes it easier to trace an order through all three consumers, but any future consumer that drops the header will break that trace. Three attempts limit repeated processing, but a healthy downstream service that remains unavailable beyond the retry window may not process the order successfully; the DLQ must be monitored and failed messages handled separately.

Persisting notification IDs improves deduplication after a restart, but reading and rewriting a JSON file is less scalable than a database. Two notification-service replicas could also race while updating the file, potentially recording the same ID twice. The current design is suitable for this assignment's single-service setup, but a production system would need stronger shared storage and concurrency control.
